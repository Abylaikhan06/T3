# T3: система аутентификации и авторизации

Backend-приложение по тестовому заданию: собственная JWT-аутентификация,
logout с отзывом сессии и управление доступом к ресурсам по ролям.

## Технологии

- FastAPI и Pydantic для REST API и проверки входных данных.
- PostgreSQL как рабочая база данных.
- SQLAlchemy и psycopg для работы с PostgreSQL.
- bcrypt для хранения hash паролей.
- PyJWT для access-токенов.

## Настройка PostgreSQL

Создайте базу и отдельного пользователя PostgreSQL:

```sql
CREATE USER t3_user WITH PASSWORD 't3_password';
CREATE DATABASE t3_auth OWNER t3_user;
```

Файл `.env` уже создан локально и не должен попадать в репозиторий. Перед
передачей проекта замените в нем пароль базы, `JWT_SECRET` и пароли тестовых
пользователей. Состав переменных показан в `.env.example`.

## Веб-интерфейс

На сайте реализованы страницы и формы для демонстрации всего основного
функционала задания:

- регистрация и вход в систему;
- личный кабинет с редактированием профиля и мягким удалением аккаунта;
- просмотр, создание, изменение и удаление доступных заказов;
- панель администратора для просмотра и изменения правил ролей.

Интерфейс использует то же защищенное API: после входа JWT сохраняется в
браузере и отправляется в `Authorization: Bearer <access_token>`.

## API

| Метод и путь | Назначение |
| --- | --- |
| `POST /auth/register` | Регистрация с ролью `user` |
| `POST /auth/login` | Вход по email и паролю, получение JWT |
| `POST /auth/logout` | Отзыв текущего JWT |
| `GET /users/me` | Получение профиля |
| `PUT /users/me` | Изменение имени или email |
| `DELETE /users/me` | Мягкое удаление: `is_active=false` и закрытие сессий |
| `GET/POST /resources/orders` | Mock-объекты бизнес-приложения |
| `PATCH/DELETE /resources/orders/{id}` | Действия над mock-объектами |
| `GET /admin/rules` | Получение правил доступа администратором |
| `PUT /admin/rules/{role}/{element}` | Изменение правил администратором |

Защищенные endpoints принимают заголовок:

```text
Authorization: Bearer <access_token>
```

Без действующей сессии возвращается `401 Unauthorized`. При наличии
пользователя без требуемого разрешения возвращается `403 Forbidden`.

## Валидация данных

- Email проверяется как email-адрес и сохраняется в нижнем регистре.
- Имя содержит только буквы, пробелы, дефисы и апострофы.
- Пароль должен содержать минимум 8 символов, верхний и нижний регистр,
  цифру и специальный символ; ограничение bcrypt составляет 72 байта.
- Пароль при регистрации должен совпадать с подтверждением.
- При обновлении профиля необходимо передать хотя бы одно поле.
- Название заказа не может состоять только из символов, а сумма должна быть
  положительной с максимум двумя знаками после запятой.
- Для изменения правил допустимы только известные роли и ресурсы.

## Таблицы и правила доступа

| Таблица | Назначение |
| --- | --- |
| `users` | Профиль, bcrypt hash пароля и `is_active` |
| `sessions` | Выпущенные JWT: `token_id`, владелец, срок и `revoked` |
| `roles` | Роли `admin`, `manager`, `user` |
| `user_roles` | Роли конкретного пользователя |
| `business_elements` | Ресурсы `orders` и `access_rules` |
| `access_role_rules` | Разрешения роли на ресурс |

В `access_role_rules` разрешения `read_permission`, `update_permission` и
`delete_permission` действуют для объектов владельца. Поля с суффиксом
`_all_permission` действуют для всех объектов. `create_permission` разрешает
создание объекта.

Начальные правила дают администратору полный доступ, менеджеру просмотр и
изменение всех заказов, а пользователю работу только со своими заказами.
Доступ к самим правилам имеет только администратор.
